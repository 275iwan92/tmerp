# Concept card: Work Order (WO)

> Written 2026-10-17 (Manufacture group). "FACT" = seen first-hand in this session: mockup DB (connection `tm2*` with `--env=mockup` = schema `ddt*`; counts = `count(*)` today) and code with line numbers. "FROM DOCUMENT" = not checked against code/DB.

- **Document type**: concept card. **Module/sub-module**: Manufacture > Planning > Work Order (`sys_app_menu` code `PROD_WO_LIST`, target `v2:production-wo`, FACT).
- **Canonical name**: Work Order = `tm2prd.prd_wo` (header) + `prd_wo_operation` (steps, card `11_card_wo-operation-bop.md`) + `prd_wo_material` (material lines, card `12_card_wo-material-bom.md`).
- **Synonyms**: WO, job, job order, perintah kerja, `wo_no` (`WO2600273`). The `mps_wo` / `prd_schedule` tables of the old system are NOT new Work Orders.
- **NOT the same as**: Customer Order (`co_order`), delivery schedule row (CPDEL, `co_order_delivery`), Delivery Order (`do_delivery`), Maintenance order (`mnt_order`), pick list (`wh_pick_list`).

## Findings (recorded, not fixed)
1. **The WO never leaves SCHEDULED in the v2 path.** `OperatorTimerService` marks operations DONE but nothing sets the header to IN_PROGRESS or COMPLETED (only the v1 page does, `tmerp_unused/production_wo_entry_v1_2026-10-20.blade.php:943`). Readers that wait for COMPLETED therefore see nothing from v2 WOs: the usage-rate engine (`UsageRateEngine.php:120,200`), and the shortage auto-detector accepts COMPLETED or a DONE last operation (`ShortageAutoDetector.php:102`). The mockup data has no finished operation, so this is NOT yet visible in numbers. FACT (grep, code).
2. **Status values with no writer**: SIMULATED, ON_HOLD, IN_PROGRESS have no v2 writer; the state machine allows DRAFT -> SIMULATED -> SCHEDULED but v2 writes DRAFT -> SCHEDULED directly. FACT.
3. **Unused columns**: `parts_id`, `source_forecast_id`, `hot_job_source`, `hot_job_customer_id`, `confirmed_at` are NULL in all 65 rows and no v2 code writes them. FACT (query, grep).
4. **32 of 55 active WOs have no `ups_per_sheet`**, no sheet size: ProDev gave no layout, and the BOM engine assumes 1 up per sheet with a warning (ATTENTION-ENGINE-01 text). Material quantities of those WOs are therefore a lower-quality estimate. FACT (query); the 1-up rule is in the engine card.
5. **Dummy data sits as `data_origin` LIVE**: all 65 WOs (and the machines) carry `data_origin = LIVE` although the database is the dummy one; the DUMMY marker would let `DataOriginScope` hide them. FACT (query); intended or not is NOT known.
6. **Primary-key names** `wo_id`, `operation_id`, `detail_id` do not follow `id_<entity>` (CLAUDE.md section 5). FACT.
7. **Delete keeps the operations and materials of a cancelled WO** (the planner skips them by status). All 10 cancelled WOs still hold their operations (1 to 9 each) and, for 8 of them, material lines. FACT (code, query).
8. **The old plan note says the WO keeps a frozen copy of grain, yield and model** (`docs/design-notes/ppic/15_ppic-tech-wo-knowledge.md` item 1 and its list of columns); `prd_wo` has no such columns. FROM DOCUMENT, wrong for the columns.
9. **A test leaves rows in the live-named database**: `ProductionWoGenerationTest::test_generate_creates_wo_with_operations_and_correct_qty` fails at cleanup (a foreign key from `prd_wo_material`), so each run leaves 1 WO, 1 material line and 1 delivery row in `tm2prd` / `tm2sdi` when it runs without `--env=mockup`. I produced two such residues in this session; see `../90_findings_planning-ppic.md`. FACT.
