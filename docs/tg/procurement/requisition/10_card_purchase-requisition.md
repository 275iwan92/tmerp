- **Document type**: concept card. **Module/sub-module**: Procurement > Requisition > Purchase Requisition (PR) (`sys_app_menu` code `PROC_PR`, target `v2:purchase-requisition`, FACT).
- **Canonical name**: Purchase Requisition = `tm2pur.pr_requisition` (header) + `pr_line` (lines) + `pr_line_alloc` (allocation of a line to a supplier; the source of PO lines).
- **Synonyms**: PR, permintaan pembelian, requisition, `doc_no` `PR2600001`, SPB-less "buy request". The tables `pr_requisition_legacy*` are the archive of the old system, not new PRs.
- **NOT the same as**: Purchase Quotation (offer from a supplier, card `../order/10_card_purchase-quotation.md`), Purchase Order (`../order/11_card_purchase-order.md`), Material Planning "Buy" (a way to make a PR, card `12_card_pr-sources-and-buy.md`).

## Relations
- **source**: department master (`org_department`), material master (`mat_raw`, category, account), COA (`fin_account`, read across databases without a FK), Material Planning / ProDev / Maintenance / Shortage follow-up as creators (card `12_card_pr-sources-and-buy.md`), `PaperPriceEngine` for the estimate.
- **used_by**: PQ (file compared per PR line, card `../order/10_card_purchase-quotation.md`), PO (allocations of APPROVED PRs, `../order/11_card_purchase-order.md`), Outstanding PR report, Material Planning netting, approval flow (card `11_card_procurement-approval.md`).
- **flows**: DRAFT -> SUBMITTED (number) -> APPROVED (default allocations) -> PQ optional -> PO line from allocation; the header never moves on after APPROVED.
- **frozen_zone**: none of the Sales frozen documents; the Goods Receipt / PO / GR-IR flow downstream is frozen (see Receive). Ask Jo before changing document statuses (CLAUDE.md section 1).

## Findings (recorded, not fixed)
1. **The PR header never leaves APPROVED.** Nothing writes PARTIALLY_ORDERED, FULLY_ORDERED or CLOSED to `pr_requisition.status`; only the line status moves. In the data, PR2600001, PR2600002 and PR2600008 (lines FULLY_ORDERED) are still APPROVED. The REMARK of `resources/views/v2/screens/purchase-requisition.blade.php` says "Closed otomatis saat semua baris jadi PO", and flow step 53 of PR (AUTO FULLY_ORDERED -> CLOSED) exists, but nothing calls `FlowEngineService::submit` with FULLY_ORDERED. Readers that exclude FULLY_ORDERED (Material Planning, PPIC) therefore never exclude a fully ordered PR. FACT.
2. **No Cancel and no Back to Draft for a PR.** `stat_cancel` / `cancel_reason` exist but no code writes them; REJECTED is a dead end (no edit, no resubmit). The lifecycle set Draft / Confirmed / Cancelled / Closed of CLAUDE.md section 3 is only partly met. FACT (grep of writers).
3. **Unused columns**: `pr_requisition.parent_pr_id`, `revision_no` (never changed from 0), `mrp_run_id` (the MRP tables were abandoned). FACT (grep).
4. **Default supplier is empty everywhere**: `mat_raw.suggest_supplier_id` is NULL on 0 of 11,401 materials, so default allocations have no supplier, the PR price from the paper engine is never used on a PR line (the engine needs a supplier), and Buy (card `12`) cannot make the PO. FACT (query).
5. **Header total can be NULL**: PR2600006 (`pr_id` 8) has `c_est_total` NULL while its lines sum to a value; the Approval Center amount for such a PR would be 0. Old dummy row (older than `recalcTotal`). FACT.
6. **Line 5 of PR2600006 is inconsistent**: `c_qty_ordered` 50 but `c_qty_allocated` 0 and `c_line_status` NULL (dummy made before the allocation rules). FACT.
7. **`PrAllocationService::split` has no screen** (class comment: "panel UI-nya menyusul"). FACT (grep).
8. **Deleting a Draft PO does not return the ordered quantity** to its PR line (see PO card finding 3). FACT (code).
9. **A Draft PR that Buy has already turned into a Draft PO line can be deleted**: the cascade removes its allocation and the FK rule sets `po_line.alloc_id` to NULL, so the PO line stays without a source PR. FACT from the FK rules and `delete` (only the DRAFT check); not run.
