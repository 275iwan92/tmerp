# Concept card: Count Task (cycle count, Stock Opname by area)

> Written 2026-10-16 (group Inventory-Warehouse). Verified: 2026-10-16. FACT = mockup DB (`ddt*` through `tm2*`, `--env=mockup`) and code with line numbers, seen this session. FROM DOCUMENT = not checked. Tests were NOT run (brief: no DB writes); test names are read from the files.

- **Document type**: concept card (a work item per stock position; the document it produces is the Stock Opname). **Module/sub-module**: Inventory > Warehouse > Count > Count Tasks (`WH_COUNT` group, `INV_WH_COUNT` `v2:wh-count-tasks`; FACT `sys_app_menu`).
- **Canonical name**: Count task = row of `tm2inv.wh_task` with `task_type='COUNT'` (number `WT` + yy + 5 digits, shared sequence with putaway tasks). One task = one position (item in one bin). The bin lock is `tm2mst.wh_loc.count_lock`.
- **Synonyms**: hitung stok, opname per area, cycle count, stock take, `count_every_days`, count lock, kunci hitung.
- **NOT the same as**: the Stock Opname report / document type `OP` (Stock group; this service creates that document), Stock Adjustment (free-form), the Stock Opname menu in Inventory.

## Relations
- **source**: `wh_zone.count_every_days`, stock positions (`WarehouseStock::positions`), stock balance (`StockTransferService::balance`), `StockDocumentService` / `StockPostingService` (Stock group).
- **used_by**: Task Board (a "Count due" card per due area, tasks per status), Stock Transfer / putaway / pick (they respect the lock), Stock Opname report.
- **flows**: area due -> Start (tasks + bin lock) -> count each position -> Confirm (difference posted as Stock Opname) -> unlock.
- **frozen_zone**: posting is the Stock group's; the count service only calls it.

## Findings (recorded, not fixed)
1. **The lock is narrower than the screen says.** The Count Tasks guide text says "nothing can be moved in or out" while the bins are locked, but goods receipts, stock in/out/return/adjustment documents and production issues do not read `count_lock`. A receipt posted into a locked bin between Start and Confirm changes the balance; because Confirm compares with the balance at confirm time, the count is then measured against moved goalposts, and `system_qty` shown on the task is stale. FACT (grep); effect not reproduced.
2. **Empty bins are not locked**: only bins that hold stock are locked at Start (`CountTaskService.php:64`), so goods can still be put away into an empty bin of an area being counted, and that stock is never counted. FROM CODE.
3. **Design says approval, code posts directly.** `docs/design-notes/inventory/06_invwh-tech-workflow-outbound.md` (FROM DOCUMENT) says "selisih menunggu persetujuan dan diposting sebagai penyesuaian bernomor"; the service posts the Stock Opname immediately with no approval step. FACT, `CountTaskService.php:110-127`.
4. **Orphan tasks**: all 12 dummy tasks reference deleted areas and bins (test residue, the screen shows "—" for area and bin). The 2 OPEN ones appear in the Task Board and the Count Tasks list but cannot be completed: Confirm reads a balance of 0 for the missing bin and, for any counted quantity above 0, `adjust()` calls `WhLoc::findOrFail` on it and would fail with a not-found error (a count of exactly 0 would book nothing and close the task). FROM CODE (`CountTaskService.php:83-85,113`); Confirm on them not tried.
5. **The lock is set outside the creating transaction** (`WhLoc::update` after the task insert transaction), so a crash in between leaves tasks without locks. FROM CODE (`CountTaskService.php:55-67`).
6. **Scheduled counting is dormant in the dummy**: no area has `count_every_days`, so `inv:count-due` and the "due" markers never trigger; Start Due Areas answers "No area is due...". FACT.
7. **No role split**: the person who starts the count, counts and confirms is any Inventory user; there is no second-person check on the difference. FACT, `routes/v2_stockflow.php:83-84` (middleware `module:INV` only).
