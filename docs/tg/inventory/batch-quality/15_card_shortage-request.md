# Concept card: Shortage Request (Permintaan Kirim Kekurangan)

> Written 2026-10-16 (group Inventory, Batch & Quality). FACT = mockup DB and code with line numbers, seen this session; no test was run. Verified: 2026-10-16.

- **Document type**: concept card. **Module/sub-module**: Inventory > Batch & Quality > Shortage Request (`INV_BQ_SHORT`, `v2:supplier-shortage`, form) and Report > Shortage by Supplier (`INV_BQ_SHRT`, `v2:shortage-by-supplier`). The code lives in `App\Services\Pur\*` because Purchasing owns the PO/receipt corrections.
- **Canonical name**: Shortage Request = one row of `tm2inv.inv_shortage_request` (model `InvShortageRequest`), number `SR` + year + 5 digits. Rule (rulebook A.26, user 2026-10-08, FROM DOCUMENT): when output + standard waste is less than the material issued to a work order, the quantity was short from the start; the system asks the source to send the shortfall, after a recount as proof.
- **Synonyms**: kurang kirim, short delivery, shortfall request, backorder request, recount, usage variance (the opposite outcome).
- **NOT the same as**: waste above standard (that is a usage variance, closed with outcome `USAGE_VARIANCE`), Purchase Return (`prt_return`), Supplier Claim (card `14_card_supplier-claim-and-trace.md`), subcon shortage correction on a service receipt (`SpecialReceiptService::reportShortage`, called by this flow for SUBCON receipts).

## Relations
- **source**: material issue documents (`rm_stock`, `rm_stock_d` via `v_inv_wo_reconcile`), work-order material standard (`prd_wo_material.cutting_yield_waste_qty`), posted receipt (`pv_receipt`, `pv_line`), PO line tolerance (`po_line.c_tol_pct`), production output (auto only).
- **used_by**: Purchasing (follow-up, backorder, debit note), PPIC (confirm), Warehouse head (recount), supplier sampling history, Shortage by Supplier report, receipt cancel guard.
- **flows**: suspicion (manual or auto) -> DRAFT -> recount -> PPIC Confirm (receipt/PO/journal/stock corrected) -> Purchasing Send -> Receive or Refuse (PO line closed, debit note Draft) -> Close.
- **frozen_zone**: Goods Receipt / PO / GR-IR flow (do not change without Jo); the shortage flow itself is a v2.01 rule (D14, D19).

## Findings (recorded, not fixed)
1. **Customer shortage does not correct the customer-owned stock.** For a CUSTOMER receipt `correctReceipt` lowers the receipt line quantity and returns before any stock correction (`ShortageRequestService.php:218-220`), so the consignment stock card keeps the original quantity. (A SUBCON receipt is a service receipt without stock, so that case is consistent.) FACT; not run.
2. **No duplicate guard on manual creation.** Only the auto-detector skips an existing WO + material pair (`ShortageAutoDetector.php:54`); `ShortageRequestService::create` and the unique index (`request_no` only) allow two requests for the same WO and material, and each Confirm would correct the receipt again. FACT.
3. **Confirm is not atomic across databases.** The receipt/PO correction (`tm2pur` transaction), the journal (`tm2acc`) and the Stock Out (`tm2inv`) run one after another, and the request status is saved last. A failure after the receipt line is corrected would leave the request DRAFT while the receipt is already reduced, so a retry would reduce it again. Whether `JournalPostingService::post` throws (rather than returns a warning) was not checked. FACT for the order; risk NOT proven.
4. **The shortage Stock Out carries no batch.** `correctStockForShortage` builds the Stock Out line with `lot_no` but not `batch_id` (`PvPostingService.php:382-398`), so batch On Hand does not fall by the shortage. FACT: the line array given to `saveDraft` (`app/Services/Inventory/StockDocumentService.php:39-55`) is stored as given, so `batch_id` stays NULL.
5. **"Received" is a click, not a check.** `receive` only needs a status of SENT; it does not verify that a goods receipt from the reopened PO line exists (the screen text says "receive it on a normal goods receipt"). FACT, `ShortageRequestService.php:139-145`.
6. **Screen and service disagree on Refuse.** The service allows Refuse from CONFIRMED and SENT; the screen shows the Refuse button only at SENT (`supplier-shortage.blade.php:119-129`). So a supplier that refuses before "Send" cannot be recorded from the screen. FACT.
7. **Window is counted from the Send click, in calendar days, and compares dates with `<`** so a request lapses the day AFTER `window_until`. FACT, `ShortageRequestService.php:133,177`.
8. **Lifecycle words differ from the rulebook.** There is no Cancelled and no Closed-by-cancel; a wrong Draft can only be dismissed with outcome "Usage variance", which also counts as no bad event. By design (FROM CODE); the common Draft / Confirmed / Cancelled / Closed set (CLAUDE.md section 3) is not followed. FACT.
9. **Debit note has no journal** (the service header says so) and the Purchase Requisition made at Confirm duplicates the reopened PO line unless Purchasing chooses one of the two (the note on the PR says "Use this OR the reopened PO line"). FACT, `ShortageFollowUp.php:25-35`; `ShortageRequestService.php:25`.
10. **Good output must be typed in material units** for manual requests; the auto-detector converts from production output only when the WO unit equals the warehouse unit (card `29_engine_shortage-auto-detector.md`). FACT.
