# Concept card: Delivery Order (DO) and Delivery Note (Surat Jalan)

> Written 2026-10-16 (group A). FACT = mockup DB (`ddt*` through `tm2*`, `--env=mockup`) and code with line numbers, seen this session. Tests run with `--env=mockup`: `DispatchLifecycleTest` (3 passed, 19 assertions), `DispatchNoMergeRuleTest` (2 passed, 10 assertions); the table row counts are the same before and after.

- **Document type**: concept card. **Module/sub-module**: Sales > Delivery > Delivery Order and Delivery Notes (`SALES_DO` `v2:delivery-order`, `SALES_DN` `v2:delivery-notes`, `SALES_DN_SUBCON` `v2:subcon-delivery-note`; FACT `sys_app_menu`).
- **Canonical name**: Delivery Order = `tm2sdi.do_delivery` (header) + `do_line` (lines). **Delivery Note / Surat Jalan** = the SAME document (one data object, two views/prints): a DO with status CONFIRMED or SHIPPED, without price.
- **Synonyms**: DO, Surat Jalan, SJ, DN, dispatch, `do_no` (`DO/26/00001`), Subcon Surat Jalan (DO of type SUBCON).
- **NOT the same as**: CPDEL (schedule, does not deduct remaining qty), Proof of Delivery (`do_delivery_pod`, card `11_card_proof-of-delivery.md`), Goods Receipt.

## Cardinality (rule A.30, Jo 2026-10-17)
Foundation: a customer DO line must come from a CO line that CPDEL has broken down into a schedule. `do_line` is the junction table.
| Pair | Cardinality | Evidence |
|---|---|---|
| DO (`do_delivery`) to its lines (`do_line`) | one to many | `do_line.delivery_id`, FK CASCADE (migration `2026_08_28_000011`, line 91) |
| `do_line` to CO line (`co_order_item`) and CO (`co_order`) | many to one; both columns NOT NULL | same migration, lines 64-65 and FK RESTRICT 92-93 |
| `do_line` to CPDEL schedule (`co_order_delivery`) | many to one; column NULLABLE (needed by SUBCON), FK RESTRICT | same migration, lines 66 and 94 |
| **DO to CO** | **many to many** through `do_line`: one DO may hold lines of several COs of the same customer (the DO list view counts `co_count = COUNT(DISTINCT co_order_id)`); one CO may be shipped by several DOs | view in the same migration, line 144; `DispatchService::pullLines` has no one-CO limit |
| **DO to CPDEL schedule** | **many to many** through `do_line`: one schedule may be fulfilled by several DOs while remaining qty exists (`qty_available = ship_qty - Σ qty_do` of PLANNED/SHIPPED lines); inside ONE DO a schedule appears once (one schedule = one line) | view `v_co_delivery_outstanding`; `DispatchNoMergeRuleTest` |
| **DN (Surat Jalan) to DO** | **one to one**: the same row; DN is the DO once it is CONFIRMED or SHIPPED, same number | `DeliveryNotePrint.php` (`number => $do->do_no`); `DeliveryNoteListGrid` |
Gap against A.30: the rule "every customer DO line has a CO and a CPDEL schedule" is enforced only by the pull (`DispatchService::pullLines`). The database allows `co_delivery_id` NULL, and `confirm` skips the schedule check for such lines. FROM CODE (`DispatchService.php:226-251`), not tested.

## Relations
- **source**: CPDEL (`co_order_delivery`), CO (`co_order`, `co_order_item`: price, description), customer/supplier master.
- **used_by**: printed Surat Jalan (QR "online document & proof of receipt"), POD (`do_delivery_pod.delivery_id`), Customer Invoice (`qty_received`), promise-accuracy KPI, Customer 360 (shipment list), `QcTraceService`.
- **flows**: CPDEL (Posted) -> pull into DRAFT DO -> Confirm (number is born, Surat Jalan ready to print) -> Shipped (CPDEL schedule SHIPPED) -> POD records the arrival and received qty.
- **frozen_zone**: DO/DN document flow (the rule freezes all flows). Read: `docs/claude_vital_flows.md` (Delivery menu).

## Findings (recorded, not fixed)
1. **DO without lines**: 2 of 2 CONFIRMED DOs in the dummy have no `do_line` (DO/26/00001 customer, DO/26/00002 subcon). `DispatchService::confirm` rejects a DO without lines, so these DOs were created outside the service (dummy). FACT (query).
2. **Data origin marker**: `DO/26/00001` has `data_origin=LIVE` although its note says "[UAT-CHAIN] dummy rantai Inquiry-Quotation-CO-Produksi" and it lives in the dummy database. FACT.
3. **Unused columns**: `price_change_approval_status` appears only in `$fillable` and is read by one screen (`delivery-order.blade.php:70`), never written. `split_from_line_id` has zero uses in `app/`, `resources/`, `routes/`. `ref_part_id` is written in one place (`ProcurementBridge.php:224`). FACT (grep).
4. **`posted_at` gate only in v2**: `DispatchService::pullLines` does not check Post to Production; only `DeliveryOrder::pull` (v2) does. The v1 path `pages::dispatch.do.entry` bypasses it. FROM CODE (CPDEL card finding 5).
5. **Cancel overwrites the note**: `cancel` writes the reason to `do_delivery.notes` (line 307), the previous note is lost. There is no `cancel_reason` column as in other documents. FACT.
6. **Status naming**: DO uses a full-word `status`, not `stat_confirm/_cancel/_close` (naming rule CLAUDE.md item 5); see the Status card. FACT.
7. **Price override without approval**: the header records `price_change_flag` but there is no approval flow (approval column empty, finding 3). Rule A.9 only limits who sees the price; whether an override must be approved is NOT checked in the documents.
8. **Vehicle/driver/weight/bundle** have no columns yet; printed empty to be filled by hand (comment `DeliveryNotePrint.php:11-14`). FACT.

9. **Marking Shipped posts no stock movement** (added 2026-10-16). `markShipped` writes only `do_delivery`, `do_line`, `co_order_delivery`; grep of `app/Services/Inventory` has no DO reference except `QcTraceService.php:32`. The inventory design note (`docs/design-notes/inventory/04_invwh-tech-movements.md` item 2) already says delivery to a customer takes stock at the item's Average; it is not built. FACT (grep).
10. **FIXED 2026-10-23: price shown on the v2 DO screen without a price-right check** (added 2026-10-16; now the screen hides Price, Subtotal, Price Source, Shipment Value and Price changes for users without `canViewSalesPrice()`, and `DeliveryOrderEntryService::updateLinePrice` ignores the edit; the invoice still bills the stored line price). Original finding: `delivery-order.blade.php` shows Price, Subtotal and Shipment Value and lets a Draft line price be edited; `canViewSalesPrice()` is called only in `DeliveryOrderPrint::load` (403), not in the screen, `DeliveryOrder.php`, or `DispatchService::updateLinePrice`. Access is limited only by the menu right. FROM CODE (grep `canViewSalesPrice`), not tested in a browser.
11. **`QcTraceService` probably looks up the wrong table** (added 2026-10-16). `prd_wo.source_delivery_id` is a CPDEL schedule id (`CoOrderDelivery::wos()` hasMany on `id_delivery`, `CoOrderDelivery.php:73`; `PpicController.php:1055` uses it with `CoOrderDelivery::whereKey`), but `QcTraceService.php:32` resolves that id against `do_delivery.id_delivery` and shows the result as `delivery_no`. Two different tables share the column name `id_delivery`, so the number shown can be another DO or empty. FROM CODE, not reproduced in the DB. The "used_by" line above says `QcTraceService` reads the DO: true, but it is the wrong key.
